# 포트폴리오 영상 가이드 — 세미휴머노이드 시뮬레이션 (STEP 3)

이 저장소의 시뮬레이션 데모 영상을 포트폴리오에 넣을 때 **어떤 파일을, 어디에, 어떤 문구로** 넣는지 정리한 문서다.
영상은 2026-11-16(장면 ①~⑤)과 2026-11-18(`semih_reach_demo` v2, `semih_dashboard_demo` v2)에 Gazebo Fortress + ROS 2 Humble(WSL2, RTX 4070 Laptop)에서 녹화했다.
녹화 과정과 문제 기록은 [semiH_troubleshooting_log.md](semiH_troubleshooting_log.md)와 포트폴리오 폴더의 `STEP3_결과보고.md`에 있다.

### `semih_reach_demo.mp4` — 무엇이 찍혀 있나

- 왼쪽: Gazebo GUI 화면(데스크톱 캡처를 잘라 1280×720). 오른쪽: **같은 회차** 로봇 카메라 프레임.
2026-11-18에 다시 녹화한 v2다. v1(2026-11-17)은 접촉 센서 없이 찍어 "표면점 2.0cm 앞에서 정지"로 표시했는데, 이후 센서로 실제로는 닿아 있었음을 확인해 같은 조건으로 다시 찍었다.
- 단계 라벨(0/4~4/4): 시작 자세 → 탐지·위치 저장(검출 10개 중앙값을 odom에 고정) → 저장 위치로 주행(0.33m에서 정지, 이후 검출 무시) → 팔 뻗기(팔꿈치 접기 → 어깨 내리기 → 펴기) → **팔 끝 링크가 가방에 접촉**.
- 오른쪽 위 "no contact / CONTACT" 표시와 아래 줄 "contact sensor (arm_link3)"은 **이 회차에 녹화하며 기록한 접촉 센서 값**(실제 시각 기록)이다. 도착 16.8초 뒤 처음 접촉했고, 기록이 끝날 때까지(약 8초) 접촉이 이어졌다. 접촉 상대는 `backpack_1` 하나뿐이었다.
- 이 회차 값: 저장 좌표 odom (2.852, -0.920, 0.093), 도착 시 목표 base_link (0.340, 0.000, 0.093), 접촉점 base_link (0.338, -0.009, 0.084), 팔 끝 좌표(링크 중심축 끝) (0.325, 0.000, 0.079), clamp 없음. 영상의 "tip axis end vs target 2.1 cm"는 중심축 끝과 목표점의 거리이고, 링크 반지름이 1.6cm라 표면은 닿아 있다.
- 오른쪽 YOLO 박스는 **녹화한 카메라 프레임에 같은 모델(YOLOv8n)·같은 임계값(0.2)으로 다시 그린 것**이다. 노드가 실시간으로 낸 박스 영상이 아니다. 이유: 노드의 기본 그림(`yolo_detection_node`)은 같은 박스의 umbrella 0.41 라벨이 backpack 0.24 라벨을 덮어서, 파이프라인이 실제로 쓴 backpack 박스가 안 보였다(v1 1차 녹화에서 확인). JPEG로 저장한 프레임이라 실시간 결과와 2순위 클래스가 조금 다를 수 있다. 팔이 카메라 앞을 가린 마지막 장면에서는 person 0.26 같은 오검출 박스도 보인다(지우지 않았다).
- 시작 위치(odom (1.87, -0.54), 가방 쪽 -21°)까지는 테스트 스크립트로 옮겼다. 영상은 그 뒤부터다.
- GUI를 켜면 시뮬레이션이 실시간보다 느리게 돈다(화면 우하단 RTF 약 18~90%). 배속 2×는 벽시계 기준이다.
- v2 녹화는 1번 했고, 그 1회분을 자르지 않고 썼다. 영상은 접촉이 시작된 뒤 7초(벽시계)에서 끝난다.

### `semih_dashboard_demo.mp4` — 무엇이 찍혀 있나

2026-11-18에 다시 녹화한 v2다. v1(2026-11-17, 39.1s)은 nav를 켠 뒤 로봇이 움직이는 장면 없이 다음 장면으로 넘어가서, Nav2 주행 장면(3/7)을 넣어 새로 찍었다.
녹화 한 번(137초)에서 장면 7개를 잘라 이었고, 아무 일도 일어나지 않는 대기 구간은 잘라냈다(Nav2 기동 대기, 목표 전송 후 출발까지 약 9초, 장면 사이). Chrome 창을 DevTools 프로토콜로 자동 조작했고, 누르기 직전에 빨간 테두리로 표시한 뒤 실제 마우스 이벤트로 눌렀다.
1. 첫 화면 — 모든 카드 정지 (1×)
2. 환경 카드: "Gazebo GUI 창도 띄우기" 체크 → nav 시작 → Gazebo 창이 뜨고 상태가 실행 중(mode nav, headless False) (1×, 창이 뜨는 구간 2×)
3. **Nav2 주행:** 목표 (2.2, -0.3, map 좌표)를 보내자 로봇이 Gazebo에서 주행해 도착 → Nav2 결과 SUCCEEDED, 도착 odom (2.223, -0.234). 출발 전 모습 1×, 주행 구간(벽시계 약 25초) 3×.
4. 새로고침 → 실행 상태 유지(상태가 브라우저가 아니라 디스크 lock 파일에 있음)
5. 인식 카드: YOLO → 3D 좌표 추출 → 팔 뻗기 순서로 시작 (2×)
6. **중복 실행 방지:** 시작 전에 열어 둔 두 번째 탭(옛 화면, 시작 버튼이 보이는 상태)에서 nav를 다시 누름 → 두 번째 실행 없이 "이미 실행 중"으로 바뀜. Gazebo 서버 프로세스 수를 누르기 전후로 셌다: 1 → 1.
7. 환경 종료 → Gazebo 창이 닫힘

- **Nav2 목표는 스크립트가 보냈다.** 대시보드에는 목표를 보내는 버튼이 없다(RViz 카드의 "2D Nav Goal"로 줄 수 있지만 녹화 자동화에서는 쓰지 않았다). 스크립트는 RViz와 같은 `navigate_to_pose` 액션을 썼고, 영상 라벨에 "sent by script"로 적었다. 목표 좌표는 사람이 정한 값이며 인식(YOLO) 결과와 무관하다.
- 주행 장면만 로봇이 잘 보이게 Gazebo 창을 크게 키우고 카메라를 가까이 옮겼다. 그동안 대시보드 창은 잠시 내렸고, 장면이 끝난 뒤 원래 배치로 되돌렸다.
- **"전체 중지" 버튼은 없다.** "환경 종료"는 Gazebo/SLAM/Nav2만 끈다. 인식 노드 3개는 카드별 "⏹ 종료"로 따로 껐다(원본 111~129초, `_raw_part2.mp4`에 있음. 편집본에서는 뺐다). 마지막에 lock 0개, 관련 프로세스 0개를 확인했다.
- 인식 노드는 원래 여러 개 동시 실행을 허용하는 설계라(카드에 "여러 개 동시 실행 가능"이라고 적혀 있음) 노드 쪽 중복 실행은 막지 않는다. 장면 6은 **환경(bringup)** 의 중복 실행 방지다.
- 이 녹화에서 인식 노드는 대시보드 기본값(클래스 필터 없음, 신뢰도 0.4, 당시 모델 `yolov8n.pt`)으로 켜졌다. 2026-11-18 녹화 이후 대시보드 기본 모델은 추가 학습 모델(`models/semih_yolov8n_ft.pt`)로 바뀌었다. 이 영상은 대시보드 조작만 보여 주고, 팔이 가방에 닿는 동작은 `semih_reach_demo.mp4`에서 보인다.
- 녹화 전용 처리: Streamlit 자체 버튼(Deploy·메뉴)은 숨겼다. 화면 뒤쪽은 단색 창으로 가렸다(다른 창이 찍히지 않게).
- 대시보드는 이 PC의 별도 가상환경(`~/semih_web_venv`, streamlit 1.65.0)에서 `127.0.0.1:8502`로 띄웠다. 저장소 코드는 바꾸지 않았다.

## 3. 함께 적어야 하는 사실 (빼면 과장이 되는 것)

- **시뮬레이션 영상이다.** 실물 로봇 영상이 아니다. 캡션이나 박스 제목에 "Gazebo 시뮬레이션"을 밝힌다.
- **배속:** 2×로 편집한 클립은 캡션에 2배속을 적는다(영상 라벨에도 표기돼 있음).
- **스크립트로 준 입력:** 사람이 실시간으로 조종한 것이 아니다.
  - SLAM 주행: 미리 정한 웨이포인트를 odom 기반 P제어로 `/cmd_vel`에 보냈다(키보드 조작 대체).
  - Nav2: 목표 4개를 `navigate_to_pose` 액션으로 보냈다(4개 모두 SUCCEEDED, 클립에는 앞의 2개).
  - 대시보드 영상의 주행: 목표 1개 (2.2, -0.3)를 `navigate_to_pose` 액션으로 보냈다(SUCCEEDED).
  - 팔 IK: `/target_point`에 목표 6개를 4초 간격으로 보냈다.
  - YOLO / 인식→팔: 로봇 이동만 스크립트, 검출·3D 좌표·팔 목표는 노드가 실제로 낸 값이다.
- **오검출이 영상에 남아 있다.** 여행가방을 traffic light로, 가까운 가방을 umbrella / person으로 잘못 분류하는 장면이 있다. 잘라내지 않았다.
- **기존 ⑤ 클립(`semih_perception_arm.mp4`)은 2026-11-16의 옛 팔(끝 링크 0.15m)로 찍은 것이라 물체에 닿지 않는다.** 최대 도달 거리에서 멈춘다. 원인은 처음에 적은 "목표가 멀어서"가 아니라 팔 설계였다 — 원래 팔은 관절 한계 때문에 팔 끝이 z 0.125m 아래로 못 내려가서, z 0.10m인 가방 목표점에는 거리와 상관없이 닿지 않았다(`semiH_troubleshooting_log.md` 14절 정정).
- **최신 반복 시험 (2026-11-18): 10회 중 10회 성공 — 포트폴리오에는 이 수치를 쓴다.** 조건: 추가 학습 YOLOv8n(`models/semih_yolov8n_ft.pt`), 접촉 센서, 같은 시작 위치, 회차마다 Gazebo 새로 실행, backpack만 인정·신뢰도 0.2. 성공 기준(시험 전에 정함): 파이프라인 완주 + clamp 없음 + 접촉 센서에 `backpack_1` 접촉. 10회 모두 같은 점(base_link (0.341, -0.009, 0.090))에서 가방에만 닿았다. backpack 신뢰도 0.56~0.99. 시뮬레이션이 결정적이라 반복 재현성이지 일반화가 아니다 — 다른 위치는 아래 9곳 결과를 따로 인용한다.
  - 문구 예: "Gazebo 시뮬레이션, 같은 시작 위치 10회 중 10회 가방 접촉(접촉 센서 확인), 이 월드 사진으로 추가 학습한 YOLOv8n 사용, 파지 없음"
- **이전 반복 시험 (2026-11-17, 사전학습 YOLOv8n, 센서 없음): 10회 중 9회 성공.** 기록용으로 남긴다. 아래 조건을 함께 적는다.
  - 성공 기준(시험 전에 정함): 탐지 고정 → 도착 → 팔 명령이 clamp 없이 끝나고, 팔 끝이 **깊이로 잰 가방 표면점** 3cm 이내.
  - 같은 월드, 같은 시작 위치, 회차마다 Gazebo를 새로 띄움(headless). 성공 9회의 팔 끝–표면점 거리 2.0~2.1cm, 오도메트리 오차(Gazebo 실제 위치 대비) 1.7~1.8cm.
  - 실패 1회(5회차): 측정된 표면점 높이가 z 0.084로 다른 회차(0.092~0.095)보다 낮아 어깨 관절이 한계(90°)에 걸려 IK가 clamp를 냈다. 팔 끝 자체는 1.9cm였지만 기준대로 실패로 셌다. 이 높이에서 작업영역 여유가 얇다는 뜻이다.
  - **이 10회 시험 때는 접촉 센서가 없었다.** 센서는 2026-11-18에 `arm_link3`에 달았고, 이후 같은 조건으로 3회(시험 2회 + 영상 녹화 1회) 돌려 **3회 모두 `backpack_1`과 접촉**을 확인했다. 접촉점은 측정 표면점과 0.2cm, 팔 끝 좌표(링크 중심축 끝)와 약 1.6cm(링크 반지름) 차이였다. 그래서 위 "2.0~2.1cm"는 못 미친 거리가 아니라 중심축 끝에서 잰 값이다.
  - 따라서 "닿았다"는 **"접촉 센서로 확인한 3회"**를 근거로 쓴다. 10회 중 9회라는 숫자에 "닿음"을 붙이려면 "9/10은 거리 기준, 접촉은 이후 3회에서 확인"처럼 나눠 적는다. 실패한 5회차(clamp)의 접촉 여부는 확인하지 않았다.
  - **다른 시작 위치(8곳, 가방 기준 90°~270°, 0.9~2.0m):** 원래 조건(backpack만 인정)으로는 **8곳 모두 검출 단계에서 실패**했다(YOLOv8n이 이 가방을 suitcase/umbrella로 봄). 인식 조건을 바꿔 backpack·suitcase·umbrella를 모두 인정하면 7곳에서 목표를 고정했고 **7곳 모두 가방에 접촉**했다(5곳은 IK clamp). 1곳은 traffic light로만 검출돼 실패. 이 결과를 쓸 때는 "인식 클래스 조건을 바꿨다"를 반드시 함께 적는다.
  - **YOLO 추가 학습 후(2026-11-18):** 이 월드에서 자동 라벨링한 사진 1,237장으로 YOLOv8n을 추가 학습했다. 원래 조건(backpack만 인정, 0.2) 그대로 원래 시작 위치 + 8곳 **모두 검출·접촉**(9/9, clamp 1곳). 학습에 안 쓴 시험 사진에서 backpack 검출률 12% → 100%. 쓸 때는 "이 시뮬레이션 월드의 물체로 추가 학습한 모델"임을 함께 적는다. 영상(`semih_reach_demo.mp4`)은 추가 학습 전 모델로 찍은 것이다.
  - **YOLO 신뢰도 임계값 0.2 조건**이다(이 가방은 backpack 0.21~0.26으로만 검출됨). 코드 기본값은 0.4 그대로다.
  - 시뮬레이션이 결정적이라 10회 결과가 거의 같다(저장 좌표 차이 2mm 이내). 다양한 위치·물체에 대한 일반화가 아니다.
  - 어느 경우든 "물체를 집는다"고 쓰지 않는다(파지 기능 없음).
- **3D 좌표 정확도:** 뎁스로 얻은 점과 물체 원점 사이 수평 거리는 의자 0.24~0.28m, 가방 0.14~0.19m다(물체 표면 기준이라 생기는 차이). 정밀도를 내세우지 않는다.
- **편집 원칙:** 각 클립은 녹화 한 번에서 연속된 한 구간만 잘랐다. 여러 시도를 이어 붙이지 않았다. 예외: `semih_dashboard_demo.mp4`는 녹화 한 번에서 장면 7개를 잘라 이었고, 장면 안의 대기 구간도 잘라냈다(라벨에 장면 번호와 배속 표기). 다른 녹화 시도의 장면은 섞지 않았다.

## 4. 쓰지 말아야 할 표현

- "실제 로봇에서 동작" / "실환경 검증" — 시뮬레이션만 했다.
- "자율 탐색(explore)" — 탐색은 시도하지 않았다.
- "인식한 물체를 집는다" / "모바일 매니퓰레이션 완성" — 파지(grasp)는 구현하지 않았다. 기존 ⑤ 클립은 도달하지 못했고, 새 코드도 도달(reach)까지만 한다.
- "10회 중 9회 닿았다" — 이전 시험(센서 없음)과 최신 시험을 섞은 표현이다. 최신은 "10회 중 10회 접촉(접촉 센서 확인, 추가 학습 모델, 같은 시작 위치)"이다.
- "성공률 100%" 단독 — "시뮬레이션, 같은 시작 위치 10회, 추가 학습 모델" 조건 없이 쓰지 않는다.
- "어느 방향에서든 인식해서 닿는다" — 확인한 것은 9곳(가방 기준 90°~270°, 0.9~2.0m)이고, 추가 학습 모델 기준이다. 사전학습 모델로는 원래 위치 1곳만 됐다.
- "YOLO 성능 100%" / "가방 인식 완벽" 단독 — 같은 시뮬레이션 월드·같은 물체에서 잰 값이다. 다른 가방·실제 카메라는 확인하지 않았다.
- "가방 표면 앞 2cm에서 정지" — v1 표현이다. 실제로는 링크 표면이 닿아 있었다(2cm는 중심축 끝 기준).
- "물체를 정확히 터치/누른다" — 힘 제어나 접촉력 측정은 없다. 위치 명령으로 뻗다가 막힌 것이다.
- "성공률 90%" 단독 — "시뮬레이션, 같은 조건 10회, 신뢰도 임계값 0.2" 조건 없이 쓰지 않는다.
- "대시보드에서 전체 중지" — 그런 버튼은 없다. 환경 종료와 노드별 종료가 따로다.
- "대시보드에서 목표를 찍어 주행" — 대시보드 영상의 목표는 스크립트로 보냈다. 대시보드는 환경을 켜고 끄는 역할이다.
- "인식한 물체로 자율 주행"(대시보드 영상 기준) — 이 주행의 목표는 사람이 정한 좌표다. 인식 결과로 접근하는 동작은 `semih_reach_demo.mp4`다.
- "중복 실행을 모두 막는다" — 막는 것은 환경(bringup)과 HDF5 수집이다. 인식 노드는 여러 개 실행을 허용한다.
- "IK 오차 0" 단독 표기 — 시뮬레이션에서 TF로 잰 값(0.0cm)임을 함께 적는다.

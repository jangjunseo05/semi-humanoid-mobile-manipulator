# 시니어 리뷰 노트 — semiH 프로젝트

오늘 P1~P4 작업을 하면서 실제로 발견하고 고친 것들을 근거로, 다음 프로젝트에도 그대로 써먹을 수 있는 일반화된 원칙 위주로 정리했습니다. "이 파일 이렇게 고쳤다"의 나열이 아니라, **왜 그게 문제였고, 다음엔 어떻게 미리 피할 수 있는가**에 집중했습니다.

---

## 1. "하루 만에 다 만들었다"는 대단한 성과지만, 그 대가가 어디로 갔는지 보세요

오늘 세션에서 실제로 재현된 버그를 세어보면: URDF/브릿지 설정 불일치 1건(odom), 발행 속도 미제어 1건(joint_states 878Hz), 동일 토픽 이중 발행 1건, QoS 미스매치 1건, XML 문법 오류 1건, 스크립트 자기 자신 오탐지 1건... 이게 "하루 만에 로봇 시뮬레이션 파이프라인 전체를 완성"한 것의 자연스러운 대가입니다. 문제가 아니라 정상입니다.

다만 여기서 배울 건: **"돌아간다"와 "검증됐다"는 다른 상태**라는 걸 프로젝트 진행 중에 스스로 계속 구분해야 한다는 겁니다. 오늘 세션 시작 시점에 당신이 이미 정확히 이렇게 정리해서 저한테 넘겨줬죠 ("완료" vs "부분 검증") — 이 습관 자체가 주니어 단계에서 가장 어려운 것 중 하나인데 이미 하고 계셨습니다. 이걸 계속 의식적으로 유지하세요.

## 2. 설정 파일 간의 "이름이 맞아야 하는" 관계는 절대 눈으로만 검증하지 마세요

가장 값진 버그였던 `/odom` 문제를 보세요 (`joint_state_bridge.yaml`):

```yaml
- ros_topic_name: "odom"
  gz_topic_name: "/model/semih/odometry"   # <- 존재하지 않는 gz 토픽
```

URDF의 실제 설정은:
```xml
<odom_topic>odom</odom_topic>   <!-- 실제 gz 토픽은 그냥 "/odom" -->
```

이 두 파일은 서로 다른 언어(YAML vs XML/xacro)로 쓰여 있고, 서로의 존재를 컴파일 타임에 검증해줄 도구가 없습니다. **문자열이 우연히 안 맞아도 아무도 에러를 안 던집니다** — ROS 쪽 `/odom` 토픽은 정상적으로 생성되고, `ros2 topic list`에도 나오고, 브릿지 프로세스도 정상 기동합니다. 그냥... 메시지가 안 옵니다.

**교훈**: 서로 다른 설정 파일이 문자열(토픽명, 프레임명, 관절명 등)로 서로를 참조할 때는, 그 문자열이 진짜 일치하는지 **반드시 실행해서 양쪽 다 찍어봐야** 합니다.
```bash
ign topic -l | grep odom          # gz 쪽 실제 이름
ros2 topic hz /odom               # ROS 쪽에 데이터가 실제로 오는지
```
"설정 파일을 다 채웠으니 됐겠지"는 절대 안전한 가정이 아닙니다. 오늘 트러블슈팅 로그 #8(SLAM이 지도를 안 그리던 문제)도 본질적으로 같은 종류의 실수였죠 — 그때도 "토픽은 있는데 TF가 없다"였습니다. **패턴이 반복되고 있다는 걸 알아채는 것 자체가 실력**입니다.

## 3. 이벤트 기반 동기화(`ApproximateTimeSynchronizer`)에 아무 토픽이나 넣지 마세요

`hdf5_collector_node.py`가 처음엔 `/joint_states`(878Hz)를 `/camera`(22Hz), `/scan`(8Hz), `/odom`과 같은 큐(`queue_size=20`)에 넣고 동기화하려 했습니다. 878Hz 토픽은 20개짜리 큐를 **23밀리초**만에 다 채우고 밀어냅니다. 카메라 프레임이 도착할 즈음엔 이미 그 시점의 joint_states는 큐에서 사라진 뒤였고요.

**일반화하면**: `ApproximateTimeSynchronizer`는 참여하는 모든 토픽의 발행 속도가 "같은 자릿수" 정도일 때 잘 동작하도록 설계된 도구입니다. 속도 차이가 한두 자릿수 이상 나면 (여기선 878Hz vs 8~30Hz, 30~100배 차이) 동기화가 아니라 **"최신값 캐싱"**을 쓰는 게 맞습니다:

```python
def _joint_state_callback(self, msg):
    self.latest_joint_state = msg   # 그냥 저장만

def synced_callback(self, img_msg, scan_msg, odom_msg):
    joint_msg = self.latest_joint_state   # 동기화된 프레임 시점에 최신값을 붙임
```

이건 임시방편이 아니라, 애초에 "완만하게 변하는 고빈도 상태값"에 대한 표준적인 패턴입니다(로봇 상태 추정에서 흔히 쓰는 sample-and-hold). 동기화가 필요한 건 "서로 다른 센서가 같은 순간을 봤다는 걸 보장해야 하는" 데이터(카메라-라이다처럼)이지, 모든 구독이 다 그래야 하는 건 아닙니다.

**질문해볼 것**: 새 토픽을 동기화 필터에 넣기 전에 "이 토픽이 몇 Hz로 오지?"를 먼저 재보세요 (`ros2 topic hz`). 답을 모른 채로 넣지 마세요.

## 4. 예외 하나가 전체를 날리지 않게 하세요 — 특히 저장/직렬화 코드에서

`hdf5_collector_node.py`의 원래 코드는 15초 동안 87개 프레임을 성공적으로 모아놓고, 저장하는 마지막 순간 `np.stack()` 한 줄이 예외를 던지면서 **87개 프레임 전부**를 날릴 뻔했습니다 (h5py context manager 덕분에 그 직전까지 쓴 데이터셋은 살아남긴 했지만, 의도한 동작은 아니었죠).

```python
try:
    f.create_dataset('camera/images', data=np.stack(self.images), ...)
except ValueError as e:
    self.get_logger().error(f'... dropping camera/images: {e}')
    # 나머지 데이터셋(라이다, joint_states, odom)은 계속 저장됨
```

**원칙**: 여러 개의 독립적인 산출물을 만드는 코드에서, 하나가 실패했다고 나머지까지 못 쓰게 만들 이유가 없다면 개별적으로 try/except를 감싸세요. "전부 성공 아니면 전부 실패"가 맞는 경우(예: 트랜잭션)와 "부분 성공이 부분 실패보다 낫다"인 경우(예: 이번 케이스, 다중 센서 로깅)를 구분하는 감각을 기르세요.

## 5. 무거운 의존성은 설치 전에 "얘가 뭘 끌고 오는지" 먼저 확인하세요

`lerobot`을 설치하기 전에:
```bash
pip index versions lerobot          # 존재/버전 확인
curl -s https://pypi.org/pypi/lerobot/0.4.4/json | python3 -c "...requires_dist..."   # 의존성 미리보기
```
이걸로 `torch`, `torchvision`, `diffusers`, `opencv-python-headless` 같은 무거운/충돌 가능성 있는 패키지가 딸려온다는 걸 **설치하기 전에** 알았고, 그래서 venv 격리를 결정할 수 있었습니다. 만약 그냥 `pip install lerobot`을 ROS 환경에 바로 돌렸다면 opencv 버전 충돌로 `cv_bridge`/YOLO가 원인 파악하기 어려운 방식으로 깨졌을 가능성이 높습니다.

**원칙**: 특히 이미 잘 작동하는 환경(오늘의 경우 하루 종일 고생해서 맞춘 ROS+Gazebo+cv_bridge 조합)에 뭔가를 추가로 설치할 때는, "이게 기존에 깔린 것과 버전이 겹치는 패키지를 요구하나?"를 설치 전에 먼저 확인하는 습관을 들이세요. 안전하지 않다고 판단되면 venv/컨테이너로 격리하는 걸 기본값으로 삼으세요.

## 6. 실측한 값을 유닛 테스트에 그대로 박아 넣으세요

`test_arm_ik.py`의 첫 번째 테스트:
```python
def test_reachable_target_is_not_clamped():
    # (0.3, 0.0, 0.35): 2026-08-04 실제 Gazebo에서 확인된 값 --
    # joints=(0, 43, -90) deg, 실제로 팔이 그 각도까지 움직이는 것까지 확인함.
    joint1, joint2, joint3, was_clamped = solve_ik(0.3, 0.0, 0.35, **GEOM)
    assert math.degrees(joint2) == pytest.approx(43.0, abs=1.0)
```

이건 그냥 "숫자가 그럴듯한지" 테스트하는 게 아니라, **오늘 실제 시뮬레이션에서 물리적으로 검증된 사실**을 코드에 고정시킨 겁니다. 나중에 누군가(미래의 당신 포함) IK 공식을 리팩터링하다가 실수로 부호를 바꾸거나 하면, 이 테스트가 "예전엔 실제로 이렇게 동작했었다"는 걸 즉시 알려줍니다. 순수 수학적으로 그럴듯한 값을 assert하는 것보다 훨씬 강력합니다.

**원칙**: 통합 테스트로 뭔가를 실측 확인했다면, 그 값을 그냥 흘려보내지 말고 회귀 테스트로 박제하세요. "오늘 확인했다"는 기록은 휘발되지만 테스트 코드는 안 휘발됩니다.

## 7. 두 개의 버그가 같은 증상으로 겹쳐 보일 수 있다는 걸 항상 의심하세요

`/odom`, `/scan`이 응답 없던 문제는 사실 **두 개의 독립된 버그**였습니다 (QoS 미스매치 + gz 토픽명 불일치). QoS를 고쳐도 `/odom`은 여전히 안 됐죠 — 왜냐면 odom 버그는 QoS와 전혀 무관한 문제였으니까요. 하나 고치고 증상이 그대로면 "내가 고친 게 틀렸나?"라고 생각하기 쉬운데, **"원인이 하나가 아니었을 수도 있다"**는 가설도 항상 같이 세워두세요.

**진단 팁**: 증상이 여러 개(여기선 `/odom`과 `/scan` 둘 다 무응답)일 때, 원인이 하나로 통일될 거라고 성급하게 가정하지 마세요. 오늘 실제로 `/scan`은 QoS 문제만 있었고 `/odom`은 QoS+토픽명 문제가 겹쳐 있었습니다 — 완전히 대칭적인 증상이 꼭 완전히 같은 원인이라는 보장은 없습니다.

## 8. 재현 가능한 진단 스크립트를 만드는 데 드는 시간은 항상 남는 장사입니다

오늘 하루 동안 같은 통합 테스트(시뮬레이션 기동 → 팔 리치 → HDF5 수집 → 검증)를 **6번 이상** 다시 돌렸습니다. 매번 손으로 명령어를 다시 치는 대신 `.sh` 스크립트로 만들어뒀기 때문에, 코드 한 줄 고칠 때마다 "진짜 고쳐졌는지"를 몇 분 만에 재확인할 수 있었습니다. 이게 없었다면 오늘 분량의 작업은 훨씬 오래 걸렸을 겁니다.

**원칙**: 뭔가를 "확인"하기 위해 3단계 이상의 수동 명령어 시퀀스를 두 번째로 반복하고 있다면, 그 시점에 스크립트로 만드세요. 특히 시뮬레이터처럼 기동에 시간이 걸리는 환경일수록 이 투자 대비 효과가 큽니다.

## 다음에 이 프로젝트를 확장할 때 (SO-101 실물 전환, MoveIt2 등) 미리 생각해둘 것

- **IK**: 지금의 `solve_ik`는 3-DOF 평면형 팔에 특화된 해석해입니다. `arm_reach_node.py`에서 이미 순수 함수로 분리해뒀으니, 나중에 MoveIt2/KDL로 바꿀 때 TF 조회·액션클라이언트·스로틀링 같은 ROS 배선은 그대로 재사용하고 `solve_ik` 호출부만 교체하면 됩니다. 지금 이 구조를 유지하세요 (미리 MoveIt2로 갈아탈 필요는 없습니다 — 3-DOF엔 과설계입니다).
- **데이터 스키마**: `action`이 지금은 팔 3관절뿐입니다. 베이스 이동까지 정책 학습에 포함시키려면 `cmd_vel`도 별도 action 필드로 넣어야 합니다 (지금 구조에 `latest_odom`처럼 latest-cmd_vel 캐싱을 하나 더 추가하면 됨 — 이미 있는 패턴 재사용).
- **fps**: `hdf5_to_lerobot.py`가 지금은 평균 간격으로 고정 fps를 억지로 만들고 있습니다 (지터 존재). 진짜 정책 학습용 데이터를 모을 거면, `hdf5_collector_node`를 이벤트 동기화 대신 **고정 주기 타이머**로 샘플링하도록 바꾸는 게 근본적으로 더 맞습니다 (joint_states에 이미 적용한 "최신값 캐싱 + 타이머" 패턴을 카메라/라이다까지 확장하면 됩니다).
